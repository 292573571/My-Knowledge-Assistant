# Java 转 AI 应用开发：逐步学习与实施计划

## 使用方式

这是一份以当前知识库项目为主线的执行计划。不要同时推进多条主线；每周只完成一个主题，并按“学习 -> 小实验 -> 接入项目 -> 测试验证 -> 复盘记录”的顺序完成。

默认节奏：每周 8 至 12 小时。

建议时间分配：

- 2 至 3 小时：阅读官方文档、理解原理。
- 3 至 5 小时：实现本周项目任务。
- 1 至 2 小时：补测试、手动验收和排错。
- 1 小时：写周报、更新任务和记录问题。

每周结束前必须满足：

1. 本周功能可运行。
2. 至少有自动化测试或可重复的手工验收步骤。
3. 有一份简短学习记录，说明学到了什么、踩了什么坑、下周做什么。
4. 不为未来假设过度设计；只解决当前阶段的真实问题。

## 当前优先级

第一目标是把系统变成可长期使用的个人学习工具，而不是先追求多 Agent、联网搜索或企业级架构。

当前先后顺序：

1. 让知识库内容可管理、可追溯。
2. 防止 AI 自动学习记录污染原始资料检索。
3. 建立 RAG 评测基线，用数据优化检索。
4. 让模型调用具备可观测性、失败处理和真实流式输出。
5. 建立受控学习工作流。
6. 再补安全、部署、权限和企业级能力。

7. 在 `notes/weekly/2026-week-01.md` 写本周复盘。

### 本周验收

- 可以用自己的话解释一条问题从前端到模型再到学习记录的完整流转。
- `mvn test` 和 `npm run build` 均通过。
- 已有架构概览和第一条 ADR。

### 学习资料

- Spring Boot 官方文档：Web、Data JPA、Configuration。
- Spring AI 官方文档：Chat Client、RAG、Vector Store。

## 第 2 周：建立文档类型与知识治理模型

### 本周目标

区分原始资料、手写笔记和 AI 自动学习记录，避免自动记录成为不可靠的主要知识来源。

### 学习内容

- RAG 元数据（Metadata）的作用。
- 为什么生成式内容不应与原始资料拥有相同可信等级。
- 文档类型、可见性、来源和版本的基本建模方式。

### 按步骤执行

1. 列出当前可进入 `docs/` 的内容来源。
2. 定义最小文档类型：
   - `source`：原始资料、官方文档、可信技术文章。
   - `manual-note`：你人工编写或确认过的笔记。
   - `learning-record`：系统自动沉淀的问答记录。
3. 决定类型如何产生：
   - `docs/learning-records/**` 自动识别为 `learning-record`。
   - 其他已有 `docs/**` 默认视为 `source`。
   - 后续由管理 API 或页面显式创建 `manual-note`。
4. 扩展 `SourceDocument` 或相关索引元数据，保存 `documentType`。
5. 确保索引重建、单文件导入、增量同步都会写入此元数据。
6. 为每种类型写一个最小单元测试：导入后能看到正确类型。
7. 写 `docs/architecture/document-metadata.md`，说明类型、来源规则和未来扩展字段。

### 本周验收

- 查询已索引文档时能够看到文档类型。
- 自动学习记录被标为 `learning-record`。
- 原始资料被标为 `source`。
- 现有导入和同步测试仍通过。

### 不做的事情

- 不要先设计复杂的多租户权限表。
- 不要为每份文档增加几十个未来可能使用的字段。

## 第 3 周：实现检索优先级和回答可信度标识

### 本周目标

让检索优先使用原始资料，并让用户清楚知道答案来自本地资料还是模型补充。

### 学习内容

- Top-K、相似度分数和候选重排的基础。
- 检索优先级与分数加权。
- Grounded Answer（有依据回答）与模型补充回答的边界。

### 按步骤执行

1. 阅读 `RagService` 当前检索、来源选择与模型回退的实现。
2. 确定最小优先级规则：
   - `source` 和 `manual-note` 的候选优先。
   - `learning-record` 仅在原始资料不足时参与，或降低最终排序分数。
3. 实现一种最简单正确的方案：先检索全部候选，再按类型调整排序；不要一开始实现复杂多路召回。
4. 在 RAG 响应中增加回答依据字段，例如：`LOCAL_KNOWLEDGE`、`MODEL_FALLBACK`、`MIXED`。
5. 前端显示清晰标识：
   - “基于本地知识库回答”。
   - “本地资料不足，以下为通用模型知识”。
   - “结合本地资料与模型补充”。
6. 编写测试：同一问题同时命中原始资料和学习记录时，原始资料排在前面。
7. 人工准备一份原始资料和一份包含不同答案的学习记录，验证引用优先级。

### 本周验收

- 自动学习记录不会在有原始资料可用时抢占主要引用。
- 用户可在回答区域一眼看出依据类型。
- 模型补充不会被展示为“知识库已证实”。

## 第 4 周：知识库管理 API 与手工验收闭环

### 本周目标

让知识库具备最小可管理性：知道导入了什么、能重建、能删除并验证删除生效。

### 学习内容

- REST API 的资源建模。
- 文档索引、源文件和向量数据的一致性。
- 删除操作的幂等性和错误处理。

### 按步骤执行

1. 盘点 `DocumentIngestionService` 已有能力：列出索引文档、单文件导入、目录同步、删除、重建。
2. 设计最小 API：
   - `GET /api/knowledge/documents`：查看索引文档。
   - `POST /api/knowledge/documents/ingest`：导入一个 `docs/` 路径。
   - `POST /api/knowledge/sync`：增量同步整个 `docs/`。
   - `POST /api/knowledge/rebuild`：重建索引。
   - `DELETE /api/knowledge/documents/{documentId}`：删除索引内容。
3. 明确删除语义：仅删除索引，还是同时删除源文件。第一版建议仅删除索引，并在 API 命名和 UI 提示中说明。
4. 为每个 API 加认证和最小的输入校验。
5. 写控制器测试或服务测试。
6. 使用真实 `docs/` 文件完成手工验收：导入 -> 提问并命中 -> 删除索引 -> 再次提问不应命中 -> 重建索引 -> 再次命中。
7. 把手工验收步骤写到 `docs/runbooks/knowledge-base-management.md`。

### 本周验收

- 可以通过 API 查询索引状态。
- 可以验证删除和重建后的检索效果。
- 删除 API 不会意外删除磁盘源文件。

## 第 6 周：建立 RAG 评测集和质量基线

### 本周目标

从“感觉回答还不错”转变为“可以量化当前 RAG 的质量”。

### 学习内容

- Recall、Precision、Faithfulness、Answer Relevance 的含义。
- 测试问题、参考答案和预期来源的设计。
- 为什么评测集必须基于真实使用问题。

### 按步骤执行

1. 从自己真实学习内容中收集 30 个问题，不要让模型先替你生成全部问题。
2. 为每个问题填写以下字段：
   - `id`
   - `question`
   - `expectedAnswerPoints`
   - `expectedSourcePaths`
   - `allowModelFallback`
   - `category`
3. 至少覆盖：Spring AI、RAG、向量检索、Prompt、Agent/MCP、项目自身架构。
4. 将数据集保存为 `docs/evaluations/rag-dataset.json`。
5. 从 30 个问题中挑选 10 个，手工运行当前系统并记录：答案、引用、是否命中正确资料、是否存在无依据内容。
6. 写 `docs/evaluations/baseline-report.md`，不要粉饰失败案例。
7. 定义当前最简单的评分方式：
   - 正确资料是否出现在引用中：是/否。
   - 回答是否覆盖预期要点：0/1/2。
   - 回答是否包含无依据断言：是/否。

### 本周验收

- 有至少 30 条真实问题。
- 有第一份基线报告。
- 能指出当前三个最常见的 RAG 失败模式。

## 第 7 周：自动化 RAG 评测执行

### 本周目标

让评测可重复运行，避免每次人工复制问题和手写结论。

### 学习内容

- JUnit 参数化测试或独立评测 Runner。
- JSON 数据集读取和报告生成。
- LLM-as-a-Judge 的适用边界。

### 按步骤执行

1. 决定评测入口：第一版建议独立 Java Runner 或测试类，不要先做前端页面。
2. 读取第 6 周的数据集，逐条调用 RAG 服务。
3. 保存每条结果：问题、回答、引用、耗时、模型回退状态。
4. 首先实现确定性指标：预期来源路径是否出现在引用中。
5. 输出 JSON 原始结果和 Markdown 汇总报告。
6. 为评测执行加入开关，避免默认 `mvn test` 调用真实模型而产生费用。
7. 可选：对少量样本引入 LLM-as-a-Judge；必须保留人工抽查，不能盲信裁判模型。
8. 写 `docs/evaluations/evaluation-runbook.md`，说明如何执行、成本风险和如何读取报告。

### 本周验收

- 可以用一个命令运行评测。
- 结果可比较、可留档。
- 默认单元测试不依赖真实模型或网络。

## 第 8 周：第一次检索优化实验

### 本周目标

通过一个明确变量的实验改善检索，而不是同时修改多项配置。

### 学习内容

- Chunk 大小和 overlap 的影响。
- Top-K 与噪声上下文的权衡。
- 实验控制变量原则。

### 按步骤执行

1. 从基线报告选择一个最突出的问题，例如“正确资料没有被召回”。
2. 选择一个变量：Chunk 大小、overlap、Top-K 或相似度阈值，只能选一个。
3. 在配置或代码中记录实验前参数。
4. 修改参数并重建索引。
5. 重新运行完整评测集。
6. 记录前后指标、成本、平均耗时及失败案例变化。
7. 决定保留还是回滚实验参数，依据数据而不是直觉。
8. 将结果写入 `docs/evaluations/experiment-log.md`。

### 本周验收

- 有一次可复现的参数实验。
- 结果包括收益和副作用，而不是只有“效果变好”。
- 可以解释为什么选择保留或回滚。

## 第 9 周：查询改写或候选重排序

### 本周目标

理解并实现一个 RAG 中间层优化能力。

### 推荐选择

优先做候选重排序；如果当前向量检索实现很简单，则先做简单查询改写。

### 学习内容

- 查询改写：将口语问题转换为更适合检索的查询。
- Reranker：先粗召回，再精排。
- 为什么重排序不等于多取几个 Top-K。

### 按步骤执行：查询改写路线

1. 为 RAG 增加可选的 query rewrite 步骤。
2. 让模型输出单条检索查询，不直接用改写结果回答用户。
3. 记录原问题、改写查询、召回结果。
4. 用评测集对比开启和关闭改写的结果。
5. 为改写失败或模型不可用设计回退：使用原始问题检索。

### 按步骤执行：重排序路线

1. 增加较大的初始候选集，例如先召回 Top-10。
2. 使用标题关键词、文本关键词或轻量规则对候选再次排序。
3. 选取最终 Top-3 到 Top-5 注入 Prompt。
4. 对比重排序前后正确资料出现在最终上下文的比例。
5. 保持规则简单、可解释，后续再考虑专用 reranker 模型。

### 本周验收

- 有开关可关闭新能力。
- 评测报告可说明它提升或损害了哪些类型的问题。
- 失败时可以安全回退到原始检索路径。

## 第 10 周：Prompt 工程与结构化输出

### 本周目标

将 Prompt 从散落在代码中的字符串升级为可测试的接口契约。

### 学习内容

- System Prompt、User Prompt、Context Prompt 的职责。
- JSON Schema 和结构化输出。
- 如何要求模型明确“不知道”和“依据不足”。
- 模型自由文本的基础质量校验、异常重试与安全兜底。

### 按步骤执行

1. 找出当前所有模型 Prompt。
2. 将每个 Prompt 的目的、变量、输出约束写入 `docs/architecture/prompts.md`。
3. 优先改造 RAG 回答输出为结构化对象，最小字段：
   - `answer`
   - `knowledgeSource`
   - `confidence`
   - `unsupportedClaims`
   - `followUpQuestions`
4. 后端解析结构化输出，解析失败时安全回退到纯文本回答。
5. 前端按字段展示，不从回答正文中猜测状态。
6. 写至少 5 个 Prompt 测试样例：资料充分、资料不足、矛盾资料、无关问题、敏感信息。
7. 用评测集验证结构化输出没有降低核心回答质量。

### 本周验收

- 关键回答状态不再依赖字符串关键词判断。
- 模型输出异常不会导致前端崩溃。
- Prompt 有文档、有版本意识、有测试样例。

## 第 11 周：真实流式响应与稳定性

### 本周目标

把当前完整回答后模拟逐字推送的 SSE，逐步升级为真实模型流式输出，并确保取消语义正确。

### 学习内容

- SSE 事件模型。
- Reactive Stream 或模型 SDK 的流式接口。
- 客户端取消、服务端取消和迟到结果处理。
- 超时、重试和背压的基础概念。

### 按步骤执行

1. 明确当前 SSE 的局限：模型先生成完整结果，再逐字发送。
2. 阅读 Spring AI 当前模型供应商的流式 API 与 `Flux` 示例。
3. 创建一个独立最小实验 API：只将模型 token 流转发给 SSE 客户端。
4. 在实验中验证：正常完成、浏览器取消、模型异常、超时。
5. 再将已验证逻辑接入现有聊天路径。
6. 保留现有执行注册表，确保停止/删除后：
   - 取消后续发送。
   - 不保存迟到助手消息。
   - 清理会话内存。
7. 将 SSE 认证从 URL Query Token 逐步迁移到更安全的 Header 或 Cookie 方案。
8. 编写取消和异常路径测试。

### 本周验收

- 首个 token 在模型生成过程中到达前端。
- 用户停止后不会继续追加内容或保存完整迟到答案。
- Token 不再出现在 URL 查询参数中，或至少有明确迁移方案与风险记录。

## 第 12 周：可观测性与模型调用可靠性

### 本周目标

让你能回答“慢在哪里、失败在哪里、用了多少成本”。

### 学习内容

- 结构化日志、Correlation ID、Trace ID。
- Spring Boot Actuator 和 Micrometer。
- 超时、重试、限流、熔断的职责边界。
- Token 使用量和成本估算。

### 按步骤执行

1. 定义统一请求 ID，并贯穿 Controller、RAG、模型调用和 SSE。
2. 记录关键指标：
   - HTTP 请求耗时。
   - 文档检索耗时。
   - 模型调用耗时。
   - 模型成功/失败数量。
   - 召回来源数量。
   - Token 用量（模型支持时）。
3. 避免记录敏感内容：不记录 Bearer Token、密码和完整私密问题。
4. 为模型调用加合理超时。
5. 对短暂网络错误实现有限次数重试；不要对用户输入错误或鉴权失败重试。
6. 模型不可用时给用户返回明确、可恢复的提示；若有本地资料，可返回资料摘要。
7. 开启 Actuator 基础健康检查。
8. 写 `docs/architecture/observability.md` 和 `docs/runbooks/model-failure.md`。

### 本周验收

- 能从同一个请求 ID 关联一次请求的主要日志。
- 能区分检索慢和模型慢。
- 模型失败时不会产生未完成或重复的聊天记录。

# 第四部分：遇到问题时的决策原则

## 什么时候应该继续实现功能

满足以下条件时继续：

- 能明确说出用户价值。
- 有清晰的最小验收条件。
- 不会引入无法验证的复杂度。
- 与当前阶段目标直接相关。

## 什么时候应该先停下来做测试或文档

出现以下情况时暂停新增功能：

- 已经不确定当前数据如何流转。
- 修改后无法证明功能是否正确。
- 同一个问题反复出现。
- 涉及删除、权限、密钥或用户数据。
- 准备一次性改动多个 RAG 参数。

## 什么时候才学习或引入新技术

- Redis：遇到缓存、限流或跨请求短期状态问题时。
- Kafka/RabbitMQ：文档解析或索引已明显变慢、需要异步和重试时。
- 专用 Reranker：基础向量检索经过评测证明召回不足时。
- MCP：已有稳定工具接口，并且需要向其他客户端暴露或复用时。
- 多 Agent：单一受控工作流已无法满足明确任务时。
- 更换向量数据库：Chroma 的过滤、规模或部署能力已成为实际瓶颈时。

不要因为技术热门就提前引入。
