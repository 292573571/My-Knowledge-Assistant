# Java 转 AI 应用开发学习与项目计划

## 1. 目标定位

目标不是学习所有 AI 技术，而是成为能够使用 Java 和 Spring AI 独立交付可靠 AI 应用的工程师。

核心能力包括：

- 使用 Spring Boot 和 Spring AI 构建大模型应用。
- 构建、评测和持续优化 RAG 知识库问答。
- 设计受控的工具调用、Agent 与工作流。
- 建设认证、权限、可观测性、安全、部署和运维能力。
- 将 AI 功能做成有真实用户价值、可验证、可维护的产品。

当前项目是主线实践项目。每学习一个主题，都应在项目中完成一个最小实现、补充测试，并留下架构或决策文档。

建议周期：6 个月；每周投入 8 至 15 小时。若每周投入更多时间，可压缩周期，但不要跳过 RAG 评测、可靠性和部署阶段。

## 2. 当前项目基础

项目已具备以下能力：

- 用户注册、登录与会话恢复。
- PostgreSQL 聊天历史持久化与用户会话隔离。
- 本地知识库优先的 RAG 问答。
- 本地知识不足时的大模型补充回答，并标注回答依据。
- 回答引用来源信息。
- 每日学习记录自动沉淀为 Markdown，并自动进入知识库索引。
- 停止生成、删除会话和迟到结果丢弃等基础边界处理。
- 后端单元测试与前端生产构建。

当前项目下一步的核心不是继续堆叠聊天功能，而是提升知识质量、可治理性、可验证性和工程可靠性。

## 3. 能力地图

| 能力层 | 要掌握的内容 | 项目对应能力 |
| --- | --- | --- |
| Java 工程基础 | Spring Boot、并发、事务、测试、数据库、缓存、消息队列 | 稳定服务、异步文档处理、任务状态 |
| LLM 应用基础 | Prompt、Token、上下文、结构化输出、流式输出、Tool Calling | 可靠问答、引用、工具调用 |
| RAG 工程 | 解析、切分、嵌入、召回、过滤、重排、评测 | 高质量私有知识库问答 |
| Agent 与工作流 | 工具调用、状态机、任务规划、人工确认、失败恢复 | 学习计划与复习工作流 |
| 生产工程 | 安全、限流、观测、成本、部署、CI/CD | 可长期运行、可排障系统 |
| AI 产品能力 | 用户场景、可信度、反馈闭环、知识治理 | 真实可用的学习工具 |

## 4. 每周固定节奏

每周建议按以下节奏执行：

1. 学习一个主题：2 至 4 小时。
2. 编写最小实验验证原理：1 至 2 小时。
3. 将能力接入项目：3 至 6 小时。
4. 补充测试、运行评测、修复问题：1 至 2 小时。
5. 写周报、技术决策和下周计划：1 小时。

每周必须有可见产出，例如：

- 新 API 或页面。
- 测试用例或评测报告。
- 架构图或技术决策记录。
- 真实失败案例与修复说明。
- 可运行的 Docker 环境或运维手册。

建议逐步建立以下目录：

```text
docs/
  architecture/  # 架构图、模块说明、数据流
  adr/           # Architecture Decision Record，关键决策记录
  evaluations/   # RAG 数据集、报告与实验日志
  runbooks/      # 启动、备份、恢复、重建索引、排障手册
notes/
  weekly/        # 每周复盘
  learning/      # 学习笔记
```

目标：防止学习发散，建立可持续的学习、实践和复盘机制。

需要完成：

1. 建立本计划中的文档目录。
2. 建立每周复盘模板。
3. 为项目写一份当前架构概览。
4. 建立技术决策记录（ADR）模板。
5. 明确近期项目定位：个人学习知识库优先，不急于实现复杂企业权限或开放式 Agent。

- `docs/architecture/overview.md`
- `docs/adr/0001-project-scope.md`
- `notes/weekly/` 下的第一份周报

验收标准：能够清楚说明项目当前模块、数据流、已知风险和未来三个月重点。

## 6. 阶段 1：构建可信的个人知识库

时间：第 2 至 5 周。

核心主题：RAG 基础、知识治理、引用可信度。

目标：让回答不仅能生成，还能让用户判断答案的可靠性。

### 学习内容

- Embedding、向量相似度和余弦相似度。
- 文档切分大小、重叠、标题层级对召回效果的影响。
- Top-K、相似度阈值、召回率与精确率。
- 上下文注入、仅基于资料回答与幻觉控制。
- 元数据过滤。
- 文档生命周期：导入、索引、更新、删除和重建。

### 项目任务

1. 为文档增加类型和元数据。
2. 至少定义三种文档类型：`source`、`manual-note`、`learning-record`。
3. 默认检索时优先使用原始资料和手写笔记。
4. 将 AI 学习记录作为降权补充，避免模型回答反复污染主知识库。
5. 为文档保存类型、来源路径、索引状态、导入时间、分块数量和内容哈希。
6. 实现知识库管理页面或最小管理 API。
7. 支持查看文档列表、索引状态、分块数量、重新索引与删除。
8. 支持查看每日学习记录。
9. 支持将有价值的问答保存为正式笔记。
10. 明确展示回答依据：
11. 基于本地知识库回答。
12. 本地资料不足，以下内容来自通用模型知识。
13. 混合回答：部分内容来自知识库，部分内容为模型补充。
14. 导入至少 10 份与 Java AI 应用开发相关的真实资料。

### 建议资料范围

- Spring AI 官方文档。
- Spring Boot 官方文档。
- RAG、向量数据库、Prompt Engineering、Agent、MCP 的官方资料。
- 自己编写的学习笔记和高质量技术文章摘要。

### 交付物

- `docs/architecture/rag-pipeline.md`
- 文档类型与检索优先级设计说明。
- 知识库管理页面或 API。
- 可浏览、编辑、删除的学习记录。

### 验收标准

- 可以导入、查询、修改、重建和删除一份文档。
- 删除文档后，文档不会再被检索和引用。
- 模型补充内容不会伪装成本地知识库结论。
- 可以解释一次回答引用了哪些片段、为什么引用。

## 7. 阶段 2：RAG 评测与检索优化

时间：第 6 至 9 周。

核心主题：用数据而不是感觉评估 RAG 质量。

目标：建立可重复的评测与迭代机制。

### 学习内容

- Context Recall：正确资料是否被检索到。
- Context Precision：检索到的资料是否相关。
- Faithfulness / Groundedness：回答是否有上下文依据。
- Answer Relevance：回答是否真正回答了问题。
- LLM-as-a-Judge 的优势、偏差与人工抽查。
- 查询改写、Hybrid Search、Reranker 的基本原理。
- 测试集泄漏和评测偏差。

### 项目任务

1. 建立 30 至 50 条真实问题组成的 RAG 评测集。
2. 每条问题记录预期答案要点、应命中的原始资料和是否允许模型补充。
3. 为项目增加评测执行入口。
4. 输出 JSON 和 Markdown 格式的评测报告。
5. 建立当前 RAG 的质量基线。
6. 依次实验以下变量，每次仅改变一个变量：
7. Chunk 大小。
8. Chunk overlap。
9. Top-K。
10. 相似度阈值。
11. 标题层级元数据。
12. 是否检索学习记录。
13. 查询改写。
14. 候选重排序或关键词与向量混合检索。
15. 建立失败案例库，记录无依据回答、资料未召回、引用错误等问题。

### 交付物

- `docs/evaluations/rag-dataset.json`
- `docs/evaluations/baseline-report.md`
- `docs/evaluations/experiment-log.md`
- RAG 参数对比表。
- 失败案例分析。

### 验收标准

- 每次检索策略调整均可量化对比。
- 不再仅凭主观体验判断 RAG 效果。
- 能解释召回、重排和生成分别影响什么。
- 能在面试中说明如何评估一个 RAG 系统是否可靠。

## 8. 阶段 3：Spring AI 与 LLM 工程化

时间：第 10 至 13 周。

核心主题：模型调用的稳定性、可控性和可观测性。

目标：从会调用模型 API，升级为能够设计可靠的模型交互。

### 学习内容

- Spring AI 的 `ChatClient`、Advisor、Memory、Vector Store 和 Tool Calling。
- System Prompt、User Prompt、Few-shot Prompt 的职责。
- Structured Output 与 JSON Schema。
- Function Calling / Tool Calling 的流程。
- 上下文窗口与 Token 预算。
- 真实流式响应、取消语义。
- 超时、重试、指数退避、限流、熔断。
- 模型空响应、截断、敏感内容拒答和模型不可用处理。
- 模型成本与模型选型。

### 项目任务

1. 将核心 Prompt 整理为可管理的模板或配置。
2. 为每个 Prompt 定义用途、输入变量、输出约束和测试样例。
3. 将核心回答升级为结构化输出，例如：

```json
{
  "answer": "回答正文",
  "confidence": "high",
  "knowledgeSource": "local_rag",
  "unsupportedClaims": [],
  "followUpQuestions": []
}
```

4. 为模型调用加入统一超时、重试与错误处理。
5. 记录模型调用耗时、Token 用量、失败率和请求 ID。
6. 使用请求 ID 串联 HTTP 请求、RAG 检索、模型调用和会话。
7. 从当前“完整回答后模拟逐字推送”升级为真实模型流式输出。
8. 保持停止、取消、删除会话时不写回迟到结果的语义。
9. 设计模型不可用时的降级策略，例如仅返回检索资料摘要。

### 交付物

- `docs/architecture/llm-request-lifecycle.md`
- Prompt 模板与测试样例。
- 模型调用日志字段规范。
- 模型异常与降级策略说明。

### 验收标准

- 模型失败或超时不会造成空白页面或脏数据。
- 能定位慢请求发生在检索、重排、模型还是传输层。
- 结构化输出降低前后端字符串解析的脆弱性。
- Prompt 被视为可版本化、可测试的接口契约。

## 9. 阶段 4：受控 Agent 与学习工作流

时间：第 14 至 17 周。

核心主题：先做受控工作流，再做开放式 Agent。

目标：从聊天问答扩展到可解释、可控制的任务完成能力。

### 学习内容

- Tool Calling 和普通函数调用的差异。
- ReAct 基本模式。
- Agent 状态、循环上限和最大工具调用次数。
- 人工确认（Human-in-the-loop）。
- 工具输入校验和最小权限原则。
- 工作流编排和状态机。
- MCP 的 Client、Server、工具发现和安全边界。
- Workflow 与自由 Agent 的适用边界。

### 项目任务

实现受控的学习助理工作流：

1. 用户输入学习主题。
2. 系统检索知识库相关资料。
3. 系统生成学习目标和知识点列表。
4. 系统生成 7 天学习计划。
5. 系统每日依据学习记录生成复习题。
6. 用户提交答案后，系统生成反馈和薄弱点。
7. 用户确认后，系统将总结保存为正式学习笔记。
8. 所有写入操作必须明确可见、可取消、可审计。

建议先实现以下工具：

- `search_knowledge_base`
- `create_learning_plan`
- `save_learning_note`，必须要求用户确认。
- `list_learning_records`
- `generate_review_questions`

本阶段不应实现：

- 不受限制的网页浏览。
- 未经确认的文件写入或删除。
- 无限循环的自主 Agent。
- 让模型直接执行 Shell、数据库写入或管理操作。
- 为了复杂而引入多智能体架构。

### 交付物

- 学习计划生成工作流。
- 复习题和学习反馈工作流。
- `docs/architecture/agent-workflow.md`
- 各工具的输入、输出、权限和失败策略说明。

### 验收标准

- 任何副作用操作均需要用户确认。
- 工具调用有最大次数、超时和错误处理。
- 系统可解释调用了什么工具、为什么调用和调用结果。
- 能清楚解释 Agent、Workflow、Tool Calling 和 MCP 的关系。

## 10. 阶段 5：生产工程基础

时间：第 18 至 21 周。

核心主题：安全、可靠性、可观测性和部署。

目标：将系统提升到具有生产工程意识的可运行项目。

### 学习内容

- Spring Security、Token 生命周期、OAuth2/OIDC。
- 密钥管理和环境配置。
- Flyway 或 Liquibase 数据库迁移。
- Docker、Docker Compose、健康检查和配置分层。
- Actuator、Micrometer、Prometheus、Grafana。
- OpenTelemetry Trace、Span 和 Trace ID。
- 限流、熔断、超时和重试。
- PostgreSQL 备份恢复。
- 向量库、索引和源文档的一致性。
- CI/CD 基础。

### 项目任务

1. 轮换并清理任何有泄露风险的 API Key。
2. 移除 IDE 配置中的敏感信息，并配置忽略规则。
3. 所有密钥通过环境变量注入。
4. 提供 `.env.example`，绝不提交真实密钥。
5. 使用 Flyway 替换 `spring.jpa.hibernate.ddl-auto=update`。
6. 统一 Docker Compose、README 与应用配置中的数据库参数。
7. 为 PostgreSQL、Chroma 和模型服务增加健康检查。
8. 为关键操作增加指标：
9. 请求总量。
10. 登录失败数。
11. RAG 检索耗时。
12. 模型调用耗时。
13. 模型错误率。
14. Token 用量和估算成本。
15. 文档导入成功率。
16. 增加 API 限流和请求体大小限制。
17. 修复 SSE Token 放在 URL 查询参数中的安全风险，改用更安全的认证方式。
18. 增加 PostgreSQL 和 Chroma 的容器化集成测试。
19. 建立备份、恢复、重建索引操作手册。
20. 配置最小 CI：后端测试、前端构建和依赖安全检查。

### 交付物

- 一键启动文档。
- `.env.example`
- 数据库迁移脚本。
- 指标说明或可观测性面板截图。
- `docs/runbooks/rebuild-index.md`
- `docs/runbooks/backup-restore.md`
- CI 配置。

### 验收标准

- 新机器可按 README 启动系统。
- 数据库结构不依赖运行时 JPA 自动更新。
- 数据库、向量库或索引异常后有明确恢复路径。
- 密钥不会进入 Git、日志、URL 或 IDE 配置。
- 能判断一次失败发生在认证、数据库、检索还是模型层。

## 11. 阶段 6：多用户隔离与企业知识空间

时间：第 22 至 24 周。

核心主题：权限模型、知识空间和数据隔离。

目标：建立企业知识库能力的核心雏形。

### 学习内容

- 多租户模型。
- RBAC 与 ABAC。
- 行级隔离和文档级权限。
- 向量数据库 Metadata Filter。
- 审计日志。
- 数据保留、导出、删除和隐私治理。
- 文件上传安全与内容扫描。

### 项目任务

1. 定义知识空间：个人空间、团队空间和公共空间。
2. 为文档、分块和学习记录添加以下元数据：
3. `ownerUserId`
4. `workspaceId`
5. `documentType`
6. `visibility`
7. `createdAt`
8. 检索时强制按当前用户和工作空间过滤。
9. 默认只能检索自己的私有学习记录。
10. 为团队资料设计共享范围。
11. 增加审计日志，至少记录文档上传、删除、共享变更、知识库重建和账号安全操作。
12. 编写跨用户隔离测试。
13. 验证用户 A 不能通过 API、会话 ID、向量检索或引用间接获取用户 B 的内容。

### 验收标准

- 个人、团队和公共资料的访问规则明确。
- 权限过滤执行在检索层，而不只是页面层。
- 有自动化测试证明跨用户知识不会泄漏。

## 12. Java 与 AI 技术学习顺序

重点不是转为算法工程师，而是强化 Java 工程能力与 LLM 应用能力的交集。

推荐顺序：

1. Spring Boot 3 与 Spring AI。
2. PostgreSQL、JPA、事务、索引和数据库迁移。
3. Redis：缓存、限流、会话和短期任务状态。
4. Kafka 或 RabbitMQ：异步文档解析、索引和失败重试。
5. Docker 与 Docker Compose。
6. 可观测性：Actuator、Micrometer、Prometheus、Grafana、OpenTelemetry。
7. Spring Security、OAuth2/OIDC 与权限模型。
8. 测试：JUnit 5、Mockito、Testcontainers 与集成测试。
9. Embedding、向量检索、RAG、评测和重排。
10. Tool Calling、MCP 与受控 Agent 工作流。
11. 云部署基础：对象存储、容器部署、配置管理和日志平台。
12. Python 最低必要能力：阅读 AI SDK 示例、写评测脚本和处理数据集。

## 13. Python 最低必要能力

生产服务可以继续以 Java 为主，但应具备阅读和验证 Python AI 生态代码的能力。

建议掌握：

- `venv`、`uv`、`pip`。
- `requests`、`pydantic`、`pandas`。
- Jupyter Notebook。
- 调用模型 API。
- 简单的数据处理和评测脚本。

目标不是转为 Python 后端，而是能够读懂、改造和验证大量 Python AI 生态中的示例、工具和评测代码。

## 14. 学习资料优先级

优先使用官方资料和原理资料，不以碎片化短视频作为主要学习方式。

第一优先级：

1. Spring AI 官方文档。
2. Spring Boot 官方文档。
3. Spring Security 官方文档。
4. PostgreSQL 官方文档中的索引、事务和隔离级别。
5. 所使用模型供应商的官方 API 文档。
6. Chroma 或目标向量数据库的官方文档。
7. Docker 官方 Getting Started 与 Compose 文档。
8. Testcontainers 官方文档。

第二优先级：

1. 《Designing Data-Intensive Applications》。
2. 《Building LLM Powered Applications》。

## 15. 每月复盘模板

每月回答以下问题：

1. 本月系统新增了什么真实用户价值？
2. 本月最重要的技术决策是什么，为什么这样选？
3. 本月遇到的最难问题是什么，如何定位和解决？
4. RAG 实际指标是否改善？
5. 当前最大的技术债是什么？
6. 哪些功能看起来高级，但没有实际用户价值？
7. 下个月最重要的一件事是什么？
8. 能否将本月工作讲成一个完整的工程故事？

这些复盘可以沉淀为技术博客、面试材料和项目文档。

## 16. 六个月后的预期成果

完成本计划后，项目应具备：

- 可管理、可更新、可删除、可重建的知识库。
- 原始资料、个人笔记和 AI 自动学习记录的明确区分。
- 有引用、有可信度标记、能提示资料不足的 RAG 问答。
- 真实评测集和量化的 RAG 优化过程。
- 结构化输出、真实流式响应、失败降级和工具调用。
- 受控学习工作流，而不是无边界 Agent。
- PostgreSQL 迁移、容器化启动、基础监控、备份恢复和 CI。
- 用户与知识库隔离的设计和测试。
- 完整的架构、决策、评测和运维文档。

最终项目应能体现以下能力：能够从用户需求出发，使用 Java 和 Spring AI 构建、评估、治理、部署并维护可靠的 LLM 应用，而不仅是调用模型 API。
