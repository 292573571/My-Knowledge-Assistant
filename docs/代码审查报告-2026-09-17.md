## 一、总体评估

| 维度 | 评分 | 说明 |
|---|---|---|
| 功能完整度 | ⭐⭐⭐⭐ | RAG 全链路、多格式解析、工作空间分层、Agent、MCP 开放均已落地 |

| 安全 | ⭐⭐ | **存在一个公网可直接利用的高危漏洞（Chroma 8000 裸奔）**；应用层鉴权设计尚可，但边界是"前缀放行"而非"默认拒绝" |

## 二、🔴 P0 — 建议立刻处理

### P0-1 数据层端口（Chroma 8000 / PostgreSQL 5432）绑定 0.0.0.0，绕过全部应用层鉴权

两个容器都把端口绑到了所有网卡，`docker ps` 实测：

```
zhihai-chroma   0.0.0.0:8000->8000/tcp, [::]:8000->8000/tcp
my-pgvector     0.0.0.0:5432->5432/tcp, [::]:5432->5432/tcp
```

**8000 端口是真裸奔**（Chroma 本身零认证），实证 —— 无需任何凭证，从公网直接执行：

```bash
# 1. 列出集合 —— 成功
curl http://175.178.229.209:8000/api/v2/tenants/default_tenant/databases/default_database/collections
# → [{"id":"d0c2dbdc-...","name":"knowledge_assistant",...}]

# 2. 读取文档块原文 —— 成功，返回真实业务内容
curl -X POST .../collections/d0c2dbdc-.../get -d '{"limit":1,"include":["documents","metadatas"]}'
# → {"documents":["Kellte工具开发使用说明\n\n| 日期 | 版本 | 说明 | 作者 |..."],
#    "metadatas":[{"workspaceId":"d574059c-...","source":"kellte开发指导说明书.docx",...}]}
```

**5432 端口有密码但暴露在公网**。协议级实测（StartupMessage 探测）要求 SASL/SCRAM 认证，**不是 trust 免密**：

```
postgres               -> 要求SASL/SCRAM
nonexistent_probe_user -> 要求SASL/SCRAM
```

故 PG 风险降级为暴力破解 / 连接耗尽 DoS / 版本 CVE，而非直接沦陷。

**含义**：应用层的 `AuthFilter` / `McpAuthFilter` / 工作空间隔离只在 nginx 那一条路径上生效。数据层这两个端口是**独立入口**，完全绕过应用。全部 586 个文档块（含原文、文件路径、工作空间 ID、内容哈希）可被匿名批量拉取；Chroma 的删除接口同源可达，存在被清空、或被投毒（写入假内容影响 RAG 输出）的风险。

**修法（前两步必做）**

1. **安全组 / 防火墙删除 8000、5432 的公网入站规则** —— 秒级生效、零停机，立即止血
2. **重建容器，端口只绑回环** —— 根治，防防火墙规则漂移
   已核实：两容器均为 `docker run` 手工启动（非 compose）；应用侧 `shihai.env` **已经用 127.0.0.1 连接**
   （`POSTGRES_URL='jdbc:postgresql://127.0.0.1:5432/postgres?currentSchema=my_knowledge_assistant'`、
   `SPRING_AI_VECTORSTORE_CHROMA_CLIENT_HOST='http://127.0.0.1'`），故改绑回环**对应用零影响**
3. `application.properties:161` 默认值改 `http://127.0.0.1` —— 仅防未来部署忘配 env（本例 env 已覆盖，非必需）

**顺带发现**：`my-pgvector` 的 restart policy 是 `no`（Chroma 是 `unless-stopped`）—— 机器重启后数据库不会自启，服务会整体不可用。

### P0-2 会话消息列表：每条消息触发一次全表扫描 + 全局锁

- 证据链：`ConversationService.java:227`（`map(messageResponse(...))`）→ `:237`（`listIndexedDocuments()`）→ `DocumentIndexStore.java:30-32`（`synchronized` + `findAllByOrderByFileNameAsc()`，无 WHERE 无 LIMIT）
- 影响：单页最多 500 条消息 ⇒ 500 次全表扫描 + 500 次全局 `synchronized` 锁竞争。这是打开任意历史会话都会走的路径，随文档量线性恶化。
- 修法：循环外只查一次并传入；`DocumentIndexStore` 增加按 `workspaceId` 查询的方法（走索引）

### P0-3 文档摄入"向量 + 索引"双写无事务，rebuild 清除顺序反了

- 证据：`DocumentIngestionService.java:1259-1260`（`vectorStore.addAll` 与 `documentIndexStore.upsertAll` 相邻，而**全类 `@Transactional` 计数为 0**）；`:724-726`（先删向量、清库，再清索引）
- 影响：中途失败会留下"索引在、向量没了"的不一致态；rebuild 中断可能留空库，且无补偿机制
- 修法：索引事务先提交 → 异步写向量 → 失败进 outbox 补偿（最小改动版：至少把清除顺序反过来，先索引后向量）

### P0-4 文档可见性判定有三套实现，且异常时静默切换

- 证据：`RagService.java:1498-1513`（按路径正则 `/user-([^/]+)/` 推 owner）、`ChromaVectorStoreAdapter.java:222-243`（按 metadata）、`InMemoryVectorStore.java:72-81`（第三套）；切换点 `ChromaVectorStoreAdapter.java:193-196`（catch 后 `fallbackSearch`）
- 影响：Chroma 抖一下就换一套判定逻辑，多用户场景下的隔离能力不可预测
- 修法：抽出唯一 `DocumentVisibilityPolicy`，三处共用

| P1-6 稀疏检索全表扫 | P0 | **P2 观察** | 586 行 / 14 MB 全表扫为毫秒级。属"未来风险"，到 5 万 chunk 量级需**换检索方案**（zhparser/pg_jieba 或 pg_bigm），而非加索引 |
| P1-7 缺索引 | P1 | **P2 观察** | 缺索引的表均在百行以内，加索引反成写放大负担。仅建议 `chat_messages` 到几万行时补 `(conversation_id, created_at)` |

**P1-6 补充说明（原报告未说清）**：该查询是
`c.search_vector @@ websearch_to_tsquery(...) or position(lower(:term) in lower(c.search_text)) > 0 (... × 12)`。
含 `position()` 的 OR 分支使 GIN 索引无法服务整个布尔表达式 —— **不是索引没建好，是该查询形态本质上用不上索引**。
作者用子串匹配兜底是因为 `'simple'` 分词器不切中文，属正确的工程权衡，非缺陷。
