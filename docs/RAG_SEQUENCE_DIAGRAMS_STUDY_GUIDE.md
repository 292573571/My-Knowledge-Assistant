# RAG 时序图学习讲解

> 配套图：[`RAG_SEQUENCE_DIAGRAMS.pdf`](RAG_SEQUENCE_DIAGRAMS.pdf)  
> 详细设计：[`RAG_SYSTEM_DESIGN.md`](RAG_SYSTEM_DESIGN.md)

## 1. 先建立一个总心智模型

这套 RAG 系统可以先不要记类名，只记住两个闭环：

```text
离线索引闭环：文件 → 文本 → 分块 → 向量 → 索引
在线问答闭环：问题 → 查询 → 候选 → 证据 → 回答 → 引用
```

第一张时序图解决：

> 一个原始文件，怎样变成可以被语义检索的知识？

第二张时序图解决：

> 一个用户问题，怎样找到可信证据，并生成可以追溯来源的回答？

两个闭环通过 `SourceDocument` 连接：

- 离线阶段生产 `SourceDocument` 分块并写入 Chroma。
- 在线阶段从 Chroma 找回 `SourceDocument`，过滤后作为模型证据。

### 1.1 一句话讲清系统

可以先背这一句：

> 系统把不同格式的文件解析成带页码和标题路径的结构化分块，使用 BGE-M3 向量化后写入 Chroma；用户提问时先改写和扩展查询，再按空间权限召回候选，以 L2 距离阈值、规则重排和 LLM 门禁筛选可靠证据，最后让模型基于证据回答，并返回文件、页码和标题路径引用。

### 1.2 必须记住的六个数字

```text
1200：单个分块最多 1200 字符
120：相邻长分块重叠 120 字符
15：每条查询先从 Chroma 取 15 个候选
5：规则重排后最多保留 Top-5
0.85：L2 距离阈值，distance <= 0.85 才能继续
3：多查询最多 3 条检索查询
```

记忆口诀：

> 一千二切片，一百二重叠；十五先召回，五个进决赛；距离零点八五，多查询不超三。

## 2. 第一张图：文件如何变成知识

第一张图是离线索引链路。虽然用户只做了一次上传，但后台会经过六个阶段：

```text
上传 → 任务化 → 解析 → 切片 → 向量化 → 持久化
```

## 3. 阶段一：上传不是直接索引

### 3.1 为什么先保存文件

用户在 Vue 页面选择文件后，前端调用：

```text
POST /api/documents/upload
```

后端不会在这个 HTTP 请求里同步完成 OCR、Embedding 和 Chroma 写入，而是先做两件事：

1. 将原始文件保存到受控的 `docs` 目录。
2. 在 PostgreSQL 中创建一条 `QUEUED` 文档任务。

接口立即把 `taskId` 返回前端，后续由前端轮询任务状态。

### 3.2 为什么要异步任务化

PDF OCR 和 Embedding 都可能耗时几十秒。同步处理会导致：

- HTTP 请求超时。
- 用户无法看到阶段进度。
- 应用重启后任务无法恢复。
- 临时网络错误无法自动重试。
- 大文件处理长期占用 Web 请求线程。

任务化后，系统可以记录：

```text
QUEUED
RUNNING
RETRY_WAIT
SUCCEEDED
FAILED
```

并显示当前阶段：

```text
PARSING
OCR
CHUNKING
VECTORIZING
PERSISTING_INDEX
```

### 3.3 `clientRequestId` 的作用

前端为每次上传生成 `clientRequestId`。如果用户重复点击或网络重试，后端可以识别同一个上传请求，避免创建多个相同任务。

这属于企业应用常见的幂等设计：

> 同一个业务请求执行多次，最终效果应该和执行一次一致。

## 4. 阶段二：解析负责理解文件结构

文件保存后，`DocumentIngestionService` 调用 `DocumentParserRouter`，根据扩展名选择解析器。

解析阶段的目标不是切片，而是：

> 尽可能忠实地把不同格式转换成统一的结构化文本表示。

统一输出为 `ParsedDocument`：

```text
documentType
content
title
blocks
```

每个 `DocumentBlock` 还可能携带：

```text
blockType
headingPath
headingLevel
pageNumber
startOffset
endOffset
```

### 4.1 PDF 解析

PDF 按真实页处理：

- 正常文本页使用 PDFBox 提取文字。
- 扫描页渲染为 300 DPI 图片后调用 Tesseract OCR。
- 文本层乱码或高度碎片化时自动回退 OCR。
- 混合 PDF 只 OCR 必要页面。
- 页码写入 `DocumentBlock.pageNumber`。
- 跨页重复的短水印、页眉和页脚会保守过滤。

为什么页码必须在解析阶段保存？

> 因为切片和向量检索以后只看到文本分块。如果解析阶段丢了页码，生成阶段无法凭空恢复正确引用页。

### 4.2 DOCX 解析

DOCX 使用文档的 body 顺序读取段落和表格，并根据 Heading 或 outline level 建立标题栈。

例如：

```text
平台架构
  故障恢复
```

对应标题路径：

```text
平台架构 > 故障恢复
```

标题路径的价值：

- 为分块补充章节语义。
- 帮助规则重排判断问题与章节是否匹配。
- 最终引用可以直接定位到文档章节。

### 4.3 HTML 解析

HTML 不会直接把整个网页的 `textContent` 写入索引，而是先清洗：

```text
script
style
noscript
template
iframe
object
embed
nav
aside
[role=navigation]
```

然后按 DOM 顺序保留：

- 标题。
- 段落。
- 列表。
- 代码块。
- 表格。

这样可以避免“首页、产品中心、热门推荐、广告入口”等导航词污染 Embedding 和检索结果。

### 4.4 图片与 OCR

PNG/JPEG 先验证文件尺寸和像素数量，再进行水印预处理和 OCR。

OCR 的现实问题是：

- `1` 可能识别成 `I`。
- `0` 可能识别成 `O`。
- 浅色水印可能混入正文。
- 小字号和复杂背景会降低识别质量。

所以 OCR 质量不能只测“是否成功”，还必须测：

> 存在少量错字时，正确问题是否仍然能够召回目标分块。

## 5. 阶段三：切片负责制造检索单元

解析得到的是完整文档和结构块，但向量库不能总以整篇文档为检索单元。

如果整篇文档只生成一个向量：

- 多主题会被平均成模糊语义。
- 检索到文档后上下文太长。
- 无法精确定位页码和章节。

所以需要切片。

### 5.1 当前切片策略

```text
最大长度：1200 字符
重叠长度：120 字符
```

不同格式使用不同切片策略：

- PDF：按页切片，不跨页。
- DOCX：按章节聚合后切片。
- HTML：按 DOM 结构块切片，表格作为整体结构块。
- Markdown：按标题章节切片。
- TXT：按段落切片。
- OCR 图片：按识别文本切片。

### 5.2 为什么需要重叠

假设一句话正好跨越切片边界：

```text
分块 A：订单服务的恢复时间目标是
分块 B：十五分钟，并由交易平台组负责
```

没有重叠时，两个分块都缺少完整语义。加入 120 字符重叠后，边界附近的信息会同时存在于相邻分块中，提高召回完整答案的概率。

代价是：

- 向量数量增加。
- 检索可能返回重复内容。
- 上下文构建需要去重。

### 5.3 切片必须保留什么

一个 `DocumentChunk` 不只是正文，还必须保留：

```text
chunkIndex
headingPath
headingLevel
pageNumber
chunkType
startOffset
endOffset
```

这些字段让系统可以回答两个不同问题：

```text
“内容是什么？”
“内容来自哪里？”
```

## 6. 阶段四：向量化把文本放进语义空间

每个 `DocumentChunk` 会被包装成 `SourceDocument`，然后交给 `ChromaVectorStoreAdapter`。

Spring AI 调用当前 Embedding 模型：

```text
BAAI/bge-m3
```

Embedding 模型把文本转换成一组浮点数。可以把这组数理解为文本在高维语义空间中的坐标。

语义相近的文本，其向量距离通常更近。例如：

```text
“恢复时间目标”
“故障后多久恢复”
```

即使没有完全相同的词，也可能在向量空间中接近。

### 6.1 为什么换 Embedding 模型必须重建索引

不同 Embedding 模型定义了不同的向量空间。

如果文档使用模型 A 生成向量，查询使用模型 B 生成向量，即使维度相同，两者坐标含义也不同，距离没有可靠意义。

因此：

> 更换 Embedding 模型后，必须重新计算全部文档向量，并重新评测距离阈值。

## 7. 阶段五：Chroma 保存向量和可追溯元数据

Chroma 不只保存向量，还保存分块正文和 metadata：

```text
documentId
fileName
chunkIndex
headingPath
pageNumber
workspaceId
ownerUserId
visibility
startOffset / endOffset
chunkType
```

这些元数据支持：

- 空间和用户权限过滤。
- 文件、页码和标题路径引用。
- 按 chunk ID 恢复正文。
- 文档删除时删除对应向量。
- 检索诊断定位具体候选。

### 7.1 为什么还有 `DocumentIndexEntry`

Chroma 负责向量检索，但应用还需要一份文档目录信息：

```text
documentId
文件路径
内容哈希
分块数
空间
可见性
索引状态
```

这份信息用于知识库列表、删除、同步和判断历史上传文档是否已删除。

### 7.2 写入顺序为什么重要

当前顺序是：

```text
写 Chroma
→ 写 DocumentIndexEntry
→ 任务标记 SUCCEEDED
```

如果配置了 Chroma，但写入失败，任务不能伪装成成功。

否则会出现：

```text
页面显示上传成功
→ 应用重启
→ 内存数据消失
→ Chroma 中没有向量
→ 文档永远检索不到
```

## 8. 第二张图：问题如何变成可信回答

第二张图是在线问答链路。可以分成六步：

```text
理解问题
→ 扩展查询
→ 召回候选
→ 筛选证据
→ 生成回答
→ 校验并引用
```

## 9. 阶段一：读取对话历史，但历史不是事实

用户调用：

```text
POST /api/rag/chat
```

`RagService` 先从 `ConversationMemory` 读取短期对话历史。

历史用于理解：

```text
它
这个
刚才的方案
上一个问题
```

但历史中的助手回答不能作为事实依据。当前 Prompt 明确要求：

> 对话历史只用于补足问题语境，事实依据必须来自本次检索到的文档。

这个边界很重要，因为历史回答本身可能已经包含幻觉。

## 10. 阶段二：查询改写和多查询提高召回

### 10.1 查询改写

用户的问题可能很口语化：

```text
“这个挂了多久能恢复？”
```

结合历史后可以改写成：

```text
“订单服务故障恢复时间目标”
```

改写的目标是生成适合检索的短查询，不是回答问题。

如果辅助模型返回空内容，系统回退到原问题，不能因为改写失败而阻断 RAG。

### 10.2 多查询

单一表达可能无法覆盖文档中的不同术语，所以系统最多生成 3 条检索查询。

例如：

```text
订单服务恢复时间目标
订单系统故障多久恢复
订单服务 RTO
```

多个查询命中同一分块时，该分块会获得小幅加分。

多查询的收益：

- 提高口语和专业词之间的匹配。
- 提高缩写、同义词和不同表述的覆盖率。

代价：

- 多次 Embedding 和 Chroma 查询。
- 延迟和成本增加。
- 候选重复，需要合并。

## 11. 阶段三：Chroma 召回候选

每条查询先向 Chroma 请求：

```text
15 个候选
```

为什么不是直接取最终 Top-5？

> 因为向量排名只是第一阶段排序。先扩大候选池，才能让后续规则重排从更多候选中找出真正有答案的正文。

### 11.1 权限过滤发生在哪里

查询 Chroma 时会附带 metadata 过滤：

```text
PUBLIC
PRIVATE + ownerUserId
WORKSPACE + workspaceId
```

这比“先召回所有文档，再在 Java 中过滤”更安全，也更准确。

如果先召回后过滤，可能出现：

```text
Top-15 全被无权限文档占满
→ Java 过滤后一个候选都没有
→ 实际有权限的文档从未进入候选
```

## 12. 最容易混淆的概念：距离不是相似度

当前 Chroma 主链路读取的是：

```text
distance
```

当前配置：

```text
score-direction=distance
similarity-threshold=0.85
```

实际判断：

```text
distance <= 0.85
```

必须这样理解：

```text
距离越小越相关
0.30 优于 0.70
0.70 优于 0.90
0.90 会被当前阈值过滤
```

错误说法：

```text
“相似度达到 85% 才通过。”
```

正确说法：

> 当前使用 BGE-M3 归一化向量在 Chroma 中的 L2 距离，经验阈值是 0.85；距离小于等于 0.85 的候选才有资格继续参与重排。

### 12.1 为什么变量还叫 `similarityThreshold`

这是一个兼容不同分数方向的通用配置名。代码同时支持：

```text
similarity：score >= threshold
distance：score <= threshold
```

当前配置选择的是 `distance`。

### 12.2 内存回退的已知风险

Chroma 不可用时，系统可以使用 `InMemoryVectorStore`。但它计算的是余弦相似度，越大越好。

当前 `RagService` 仍按全局 `distance` 方向处理分数。因此：

> 内存回退只能视为开发或可用性兜底，不能假设它和生产 Chroma 具有相同质量语义。

这是后续企业化应优先统一的分数协议问题。

## 13. 阶段四：候选去重、过滤和规则重排

### 13.1 去重

多个查询可能命中同一个分块。系统使用以下稳定键去重：

```text
documentId#chunkIndex
```

重复命中会获得小幅分数奖励，但不会把同一分块重复放入上下文。

### 13.2 进入重排前的过滤

系统会排除：

- 学习记录。
- 已晋升的每日学习笔记。
- 包含通用模型免责声明的内容。
- 空正文。
- 只有 Markdown 标题、没有实质内容的分块。
- 不包含问题中显式技术缩写的候选。
- L2 距离大于 0.85 的候选。

### 13.3 当前规则重排

当前没有 Cross-Encoder Reranker。规则分数主要由以下部分构成：

```text
(1 - distance) * 10
+ 问题词面命中
+ 正文质量
+ 文档类别优先级
+ 针对部分知识主题的标题和正文 Boost
```

然后最多保留：

```text
Top-5
```

为什么标题不能总排第一？

> 标题和问题可能高度相似，但标题本身通常没有答案。规则重排会降低“只有标题”的候选，提升包含解释、步骤和事实正文的候选。

### 13.4 LLM 候选相关性门禁

规则重排后的 Top-5 还要经过 `RagQualityGate`。

模型只能返回：

```text
KEEP: 1,3
KEEP: none
```

这一步不是生成答案，而是判断哪些候选能直接支持当前问题。

如果输出格式无法解析，系统采用保守策略：

```text
全部拒绝
```

原因是：

> 宁可转入无本地证据路径，也不能把无法确认相关的内容伪装成知识库依据。

## 14. 阶段五：有证据和无证据走不同路线

### 14.1 没有可靠本地证据

如果最终来源为空，当前配置允许使用通用模型回答。

此时必须满足：

- 不返回本地 `sources`。
- 不伪造知识库引用。
- 在回答后统一添加：

```text
以上回答基于通用大模型知识，不是当前知识库内容。
```

### 14.2 有可靠本地证据

系统把最终来源格式化进 Prompt，当前显式包含：

```text
source
path
chunkIndex
pageNumber
title
content
```

`headingPath` 已保存在 `SourceDocument` 和最终引用中，但当前尚未显式写进生成 Prompt。这是设计文档中已经记录的改进点。

Prompt 由四部分组成：

```text
系统提示
对话历史
文档上下文
用户问题
```

模型被要求：

- 先给直接结论。
- 只使用上下文中的事实。
- 忽略无关、重复和仅标题片段。
- 不把文档中的问题句当成答案。
- 证据不足时明确说明缺少什么。

## 15. 阶段六：回答后还要校验依据

模型生成候选回答后，`RagQualityGate` 再检查一次：

```text
PASS
FAIL
```

检查目标：

- 是否直接回答当前问题。
- 每个关键结论是否有资料支持。
- 是否把资料中的问题误当答案。
- 是否出现资料外的关键事实。

如果是 `FAIL`，系统不会把错误答案带着本地引用返回，而是转入通用模型回退。

如果是 `PASS`：

1. 把最终来源转成 `RagSource`。
2. 追加人类可读的参考来源。
3. 保存本轮对话记忆。
4. 返回答案和结构化引用。

引用可以包括：

```text
文件名
第 N 页
标题路径
分块编号
片段
分数
```

## 16. 一次错误回答应该怎样定位

最重要的方法：

> 从链路前面向后检查，找到第一个错误阶段。

不要看到最终回答错误，就直接修改 Prompt。

### 16.1 第一步：检查解析

打开“解析文本预览”：

```text
正确答案是否存在？
页码是否正确？
DOCX 标题路径是否保留？
HTML 导航是否被清理？
OCR 文字是否可理解？
表格表头和目标行是否完整？
```

如果答案根本不在解析文本中，这是解析问题。

典型例子：

```text
扫描 PDF 没有触发 OCR
OCR 把关键编号识别错
DOCX Heading 没有识别
HTML 把导航当正文
表格解析丢失表头
```

### 16.2 第二步：检查召回

如果解析文本正确，再看检索诊断：

```text
正确 documentId/chunkIndex 是否进入候选？
```

如果没有进入候选，这是召回问题。

可能原因：

- 查询改写丢失关键词。
- Embedding 对编号或专有词不敏感。
- 单查询候选 15 个仍不够。
- 文档和查询使用了不同 Embedding 模型。
- 空间权限 metadata 错误。
- Chroma 索引中没有目标向量。

### 16.3 第三步：检查过滤与重排

如果正确分块出现在候选中，但：

```text
usedInContext=false
```

就是过滤或重排阶段的问题。

检查：

- `distance` 是否大于 0.85。
- 是否被显式技术术语过滤。
- 规则重排是否把它挤出 Top-5。
- LLM `KEEP` 门禁是否误拒绝。
- 质量门禁是否返回了无法解析的格式。

### 16.4 第四步：检查生成

如果正确分块已经：

```text
usedInContext=true
```

并且上下文足够回答，但模型仍然回答错误，这才是生成问题。

可能原因：

- Prompt 约束不清楚。
- 上下文重复或太长。
- 模型忽略证据。
- 多个来源互相冲突。
- 主模型失败后备用模型质量下降。
- 回答依据门禁漏检。

### 16.5 第五步：检查引用

如果答案正确，但文件、页码或标题路径错误，这是引用问题。

沿着元数据链检查：

```text
DocumentBlock
→ DocumentChunk
→ SourceDocument
→ Chroma metadata
→ RagSource
```

引用信息不会由模型自动推断，而是来自这条结构化元数据链。

## 17. 四类错误的快速判断表

| 观察结果 | 问题阶段 | 优先检查 |
|---|---|---|
| 解析预览中没有正确内容 | 解析 | Parser、OCR、格式清洗 |
| 解析正确，但候选中没有目标分块 | 召回 | 查询、Embedding、Chroma、权限、候选数 |
| 候选有目标分块，但 `usedInContext=false` | 过滤/重排 | 阈值、规则分数、Top-5、LLM KEEP 门禁 |
| 目标分块已用于上下文，但回答仍错 | 生成 | Prompt、上下文、模型、回答依据门禁 |
| 答案对，但页码或标题路径错 | 引用 | 结构元数据传递链 |

记忆口诀：

> 预览无内容看解析，候选无目标看召回；候选有而没使用看重排，证据用了还答错看生成；答案正确位置错看引用。

## 18. 用五个质量评测理解系统

当前多格式评测集不是只检查最终答案，而是在验证整个链路。

### 18.1 PDF 页码

验证：

- 正确内容在第 2 页解析出来。
- 检索候选保留第 2 页。
- 最终引用也是第 2 页。

这同时测试解析、切片、Chroma metadata 和引用映射。

### 18.2 DOCX 标题路径

要求：

```text
平台架构 > 故障恢复
```

这测试 Heading 识别、标题栈、章节切片和引用元数据。

### 18.3 HTML 导航噪音

正文需要命中，但候选不能出现：

```text
产品中心
热门推荐
广告入口
```

这测试 HTML 清洗是否发生在向量化之前。

### 18.4 OCR 错字召回

问题使用正确编号 `C-17`，样本保留识别型错误 `C-I7`。

目标不是要求 OCR 完全无错，而是验证：

> 存在有限错字时，语义和周边关键词是否仍能让目标分块进入候选。

### 18.5 表格表头和对应行

评测要求以下内容出现在同一个候选：

```text
服务名称
恢复目标
责任组
订单服务
十五分钟
交易平台组
```

如果表头和目标行被切到不同分块，模型可能无法判断“十五分钟”对应哪个字段。

## 19. 10 分钟口述稿

下面这份内容可以直接用于面试或项目讲解练习。

### 第 1 分钟：系统目标

我的项目是一个支持多知识空间的企业级 RAG 知识助手。系统需要把 PDF、DOCX、HTML、图片和普通文本转成可检索知识；用户提问后，根据当前用户和空间权限召回可靠证据，让模型基于证据回答，并返回文件、页码和标题路径等引用。

整套系统分成两个闭环：离线索引和在线问答。离线链路是文件、文本、分块、向量、索引；在线链路是问题、查询、候选、证据、回答、引用。

### 第 2～3 分钟：上传和解析

上传接口不会同步执行全部处理。后端先把文件保存到受控的 docs 目录，再用 clientRequestId 创建幂等的 PostgreSQL 异步任务，立即向前端返回 taskId。后台任务支持状态、阶段、租约、自动重试和应用重启恢复。

解析阶段按格式路由。PDF 按页提取文本，扫描页和乱码文本层回退到 300 DPI OCR，并保留真实页码；DOCX 按 body 顺序解析段落和表格，通过 Heading 建立标题路径；HTML 清理脚本、样式、导航和侧栏后保留标题、段落、列表、代码和表格；图片经过尺寸校验、水印预处理和 OCR。

### 第 4 分钟：切片和向量化

解析结果统一表示为 ParsedDocument 和 DocumentBlock。格式专用 Chunker 把结构块切成最多 1200 字符、重叠 120 字符的分块。PDF 不跨页，DOCX 按章节，HTML 保留表格块。每个分块都携带页码、标题路径、块类型和 offset。

分块使用 BAAI/bge-m3 生成 Embedding，随后写入 Chroma。Chroma 同时保存正文和 documentId、chunkIndex、pageNumber、headingPath、workspaceId、ownerUserId、visibility 等 metadata。应用还会保存 DocumentIndexEntry，用于文档列表、删除、同步和索引状态管理。

### 第 5～6 分钟：查询和召回

用户提问后，系统读取短期对话历史来理解代词，但历史助手回答不能作为事实依据。当前开启查询改写和多查询，最多生成 3 条检索查询。每条查询先从 Chroma 取 15 个候选，并在向量库查询阶段按用户、空间和可见性过滤。

当前 Embedding 模型是 BGE-M3。Chroma 返回的是归一化向量的 L2 distance，越小越相关，不是相似度。当前阈值是 distance 小于等于 0.85，0.85 不能解释为 85% 相似度。

### 第 7～8 分钟：过滤和重排

多查询结果按 documentId 和 chunkIndex 去重，重复命中会获得小幅加分。之后排除学习记录、模型免责声明、空正文、只有标题的分块和显式技术术语不匹配的内容，再应用 0.85 距离阈值。

当前没有 Cross-Encoder。系统使用向量距离、词面命中、正文质量、文档类别和部分主题规则进行重排，最多保留 Top-5；然后再由 LLM 候选门禁返回 KEEP 编号列表，只让能直接支持答案的片段进入上下文。

### 第 9 分钟：生成和引用

如果没有可靠本地来源，系统可以使用通用模型回答，但不返回本地 sources，并明确标记回答不是当前知识库内容。如果有可靠来源，则把文件、路径、分块、页码、标题和正文拼入 Prompt，让模型只根据证据回答。

模型生成后还会经过回答依据校验。通过后才返回 RagSource 和可读引用；失败则转入通用模型回退，避免把无依据回答和本地引用绑定在一起。

### 第 10 分钟：错误定位和质量

错误回答不能一律归因于模型。我的定位顺序是：先看解析预览，内容不存在就是解析问题；解析正确但候选没有目标分块是召回问题；候选存在但 usedInContext 为 false 是阈值、重排或候选门禁问题；正确分块已进入上下文但仍答错才是生成问题；答案正确但页码或标题错误是引用元数据问题。

项目已经用多格式评测集覆盖 PDF 页码、DOCX 标题路径、HTML 导航噪音、OCR 错字召回和表格表头同行命中，并已引入关键词检索与 RRF，解决编号、OCR 和表格仅依赖向量召回的不足。

## 20. 记忆卡片

### 卡片 1

**问：RAG 的两个闭环是什么？**

答：离线索引是文件到向量索引；在线问答是问题到证据、回答和引用。

### 卡片 2

**问：为什么上传要异步任务化？**

答：OCR 和 Embedding 耗时长；异步任务支持快速响应、阶段进度、重试、租约和重启恢复。

### 卡片 3

**问：解析和切片有什么区别？**

答：解析负责把格式转换成带结构的统一文本；切片负责把结构文本变成适合向量检索的最小单元。

### 卡片 4

**问：当前切片参数是什么？**

答：最大 1200 字符，重叠 120 字符。

### 卡片 5

**问：为什么 PDF 不跨页切片？**

答：保证每个分块有唯一、真实的引用页码。

### 卡片 6

**问：当前 Embedding 模型是什么？**

答：`BAAI/bge-m3`。

### 卡片 7

**问：为什么换 Embedding 模型必须重建索引？**

答：文档向量和查询向量必须在同一个模型定义的向量空间中，阈值也与模型和距离分布绑定。

### 卡片 8

**问：Chroma 当前返回距离还是相似度？**

答：距离。当前读取 `distance`，按 BGE-M3 归一化向量的 L2 距离解释，越小越相关。

### 卡片 9

**问：0.85 代表什么？**

答：L2 距离经验阈值，`distance <= 0.85` 才通过；不是 85% 相似度。

### 卡片 10

**问：为什么每条查询先取 15 个，最后只留 5 个？**

答：先扩大召回池，再用过滤和规则重排选择有实质答案的 Top-5。

### 卡片 11

**问：当前重排是不是 Cross-Encoder？**

答：不是。当前是项目规则重排加 LLM 候选相关性 KEEP 门禁。

### 卡片 12

**问：没有本地证据时怎么办？**

答：可以转通用模型回答，但不返回本地引用，并明确标记不是当前知识库内容。

### 卡片 13

**问：正确候选存在但 `usedInContext=false` 属于什么问题？**

答：过滤、阈值、规则重排或 LLM 候选门禁问题，不是原始召回问题。

### 卡片 14

**问：正确证据已经用于上下文但仍答错，属于什么问题？**

答：生成、Prompt、上下文组织、模型或回答依据门禁问题。

### 卡片 15

**问：引用页码从哪里来？**

答：从 Parser 的 DocumentBlock 开始，经 DocumentChunk、SourceDocument、Chroma metadata，最终进入 RagSource，不是由模型猜测。

## 22. 自测题参考答案要点

1. 多格式文档结构化切片并向量化，按权限召回证据后生成带引用回答。
2. 文件→文本→分块→向量→索引；问题→查询→候选→证据→回答→引用。
3. 避免 HTTP 超时，支持进度、重试、租约和恢复。
4. 前者统一格式并保留结构；后者制造检索单元。
5. 后续阶段无法可靠推断原始页码。
6. 通过 Heading/outline level 维护标题栈。
7. 避免导航和广告污染 Embedding 与召回。
8. 1200 / 120。
9. `BAAI/bge-m3`。
10. workspace、owner、visibility、文件、分块、页码、标题路径等。
11. 回退原问题。
12. 覆盖同义词、口语、缩写和不同文档表达。
13. 15。
14. 5。
15. L2 distance，越小越好。
16. 它是距离空间中的经验阈值，不是百分比相似度。
17. 按文档和分块去重，并给予小幅重复命中奖励。
18. 学习记录、免责声明、空内容、仅标题、术语不匹配和超阈值候选。
19. 距离、词面命中、正文质量、类别和定向 Boost。
20. 只允许能直接支持答案的候选进入上下文。
