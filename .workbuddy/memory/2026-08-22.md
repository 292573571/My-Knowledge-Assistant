## 对话流式输出体检 + 首字延迟优化（A + B）
- 用户反馈：对话回复慢、且"感觉一次性拿到所有答案"，怀疑流式没生效。
- 诊断结论：**流式本身已生效（前后端都对），"一次性"是首 token 延迟（TTFT）太高 + 期间无进度反馈造成的错觉**。
  - 后端：`LocalChatClient.stream()` 返回 `Flux<String>`；`LearningAssistantController.stream` / `WorkbenchStreamController.stream` 用 `SseEmitter` 逐 token 发。
  - 前端：`learningAssistantApi.js` 用 `fetch + getReader()` 真流式读取；`LearningAssistantPage.vue` `assistant.content += data.text` 实时渲染。
  - 根因：`RagService.stream()` 在吐字前同步做完 ① `resolveConversationContext`（多轮时无条件调一次 LLM 做指代改写，line 944）② 向量检索 ③ 阈值/技术词过滤；这些步骤一个 token 都不发，前端只转圈。且 LearningAssistant 路径**无任何"正在检索"进度事件**（Workbench 路径发了 tool_call 事件但前端没接）。
- 实施 A（检索进度反馈）：`LearningAssistantController.stream` 在调 service 前发 `tool_call_start(rag_retrieve)`，service 经 `WorkbenchChatService.streamChat` 新增的 `Consumer<List<RagSource>> onSources` 回调把 sources 回传，controller 再发 `tool_call_result` + 每个 `source` 事件；前端 `LearningAssistantPage.vue` 用 `assistant.retrieving` 标志 + `ChatMessage.vue` 显示"正在检索知识库，请稍候…"替代黑屏转圈。
- 实施 B（砍首字延迟）：`RagService.stream()` 把 `resolveConversationContext`（LLM 指代改写，可能 2-5s）用 `CompletableFuture.supplyAsync` 丢到另一线程，与**基于原问题**的向量检索并行；改写回来后再补一次轻量扩展检索并 `stableSourceKey` 去重合并。检索质量不变（`retrieveCandidates` 传 null 安全，基础查询恒用原 question，standaloneQuestion 仅增量扩展）；`retrieveCandidates` 仍在主线程调用，不触碰 `retrievalTrace` ThreadLocal。history 承接为 `final contextHistory` 供 lambda 使用。
- 验证：`mvn -o test` 307 全过（BUILD SUCCESS）；`yarn build` 通过。编译曾报 history 非 effectively final，已用 final 承接变量修复。
- 未提交、未 push、未重新部署（用户未要求发版）。TTFT 实际降幅需部署后观察（本地无模型 key / 日志需 sudo 不可得）。
